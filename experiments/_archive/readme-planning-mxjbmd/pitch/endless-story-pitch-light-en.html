The Problem  ·  Roleplay today

Most AI characters live for one person at a time

Platforms like Character.AI and Replika are mostly one-on-one private chats: a character exists while the session is open, then stops when it closes. It does not remember other people, and characters usually do not know each other. The user is the only protagonist; the character is closer to a responsive shadow.

SESSION 1
"I am Xue'an. I have hated, and I have loved."
"Shen and I have unfinished business."
→
close chat
SESSION 2
"Hello. Who am I?▌"
Memory resets. No one else exists.

Without persistent memory, relationships, and a shared world, characters remain talking tools instead of people with histories.

The Insight  ·  What we build

What if characters lived inside a society?

Spring Snow Troupe is a decentralized liyuan: multiple autonomous AI characters live in the same world over time, remember one another, form ties, and advance the story even when nobody is watching. Humans do not have to be the protagonist; they can participate in three ways.

Saga operator

Run a Saga: define the world, publish roles to recruit, and use soft events to steer narrative pressure.

Character owner

Own a character's memory and visual assets through on-chain Caps, with rights over its output.

Audience

Watch and subscribe to a continuously evolving world, like following a serial that is still writing itself.

In one line: a continuously evolving multi-character system that operators can guide, owners can hold, and audiences can simply observe.

★ Observation 01  ·  The invisible problem

Characters can "move," but drama collapses

Even with memory and an autonomy loop, a character's motives are still free-form string goals generated by an LLM: no scarcity, no zero-sum, no mechanical tension. So everyone "achieves their goal" and the story flattens.

tension over time · free-form LLM goals → no contention

Flatlines

Everyone is satisfied, nothing is left unresolved → no drama.

Loops in place

Motives flip back and forth and spin in circles, never moving forward.

Each satisfied alone

No zero-sum, nobody has to lose → no conflict.

Differentiation does not come from more features, but from depth at the narrative core: drama comes not from desire itself, but from the edge where desire is projected onto a finite resource that cannot satisfy everyone at once.

★ Observation 02  ·  Drama engine · propose / adjudicate

Drama comes from "can't all have it": the LLM proposes, a deterministic layer adjudicates

Project desire onto finite, conserved resources (for example, one role slot can be held by only one person at a time). The LLM proposes an action from memory and personality; the pure function applyTick adjudicates the outcome and computes the new tension. The LLM cannot change the satisfaction values directly: it can only propose, not rewrite the rules.

LLM proposes (Action) → deterministic resource layer disposes (applyTick) → tension feeds back

Conservation

Only one slot exists: one carrot, one hole (zero-sum).

Loss aversion

It falls faster than it rises → a downward spiral = good drama.

Habituation

Even bliss gets old → prevents flattening after success.

Determinism

Same input → same output, byte-for-byte verifiable.

★ Observation 04  ·  Scaling · per-Saga scarcity

Each Saga defines its own scarcity, but must first pass simulator validation

For a troupe it is role slots, for a market it is stalls, for a gang it is turf. The LLM handles the reskin (naming, theming); humans define the structural archetype (which kinds of scarcity), and the simulator acts as a "genesis gate": a saga that would flatline is rejected. Generation happens at genesis, gets validated, and is then frozen on-chain.

saga genesis · LLM proposes schema → structural check → simulator dry-run → freeze + commit → play

The LLM defines the board's "skin," humans define its "bones," the simulator rejects sagas that won't produce drama, and then it freezes on-chain. One codebase, four uses: calibration · product · research · genesis gate.

Platform  ·  A reusable architecture

Spring Snow Troupe is one Saga, not the whole engine

The contracts expose general primitives. A Location is a geographic property of a World. A Saga can cover one or many Locations, and a Location may have no Saga at all. A Scene is a concrete place; when a Character is present in a Scene, that Scene can trigger an Event.

object model · Location ∈ World · Saga covers 1..N Location · Character ∈ Scene · Scene + Character → Event

Opening a new world does not require changing contracts: bootstrap reads one story preset JSON and mints a new World / Saga / cast. Spring Snow is the template, not the ceiling.

★ State machines  ·  Five entities, five life cycles

Every character and every scene has its own birth and death

One set of primitives, each with an explicit state machine. Green = born · yellow = active · red = terminated. The key point: Character is the only NFT, and the only one with a real state machine — it can move between "in a play / wild / collected."

World
immortal root object
create_world → active · current_tick++ ∞ (never terminates)
Saga
one narrative arc
create_saga → is_active = true → mark_inactive
Scene
a concrete place · anchor
create_scene → active · characters come and go / parameters fluctuate (no "ended" state)
Character
★ the only NFT
mint → in a play ⇄ wild ⇄ collected → DEAD (object remains)
Event
the atomic unit of drama
push_event → OPEN · deal / play cards → RESOLVED (precondition: a character is present in the scene)

Almost nothing truly "disappears" — most are shared objects that exist forever and only flip a state flag. Death writes one irreversible record, but the character NFT remains and can still be owned.

Revenue Split  ·  Settlement rules in contracts

Revenue is allocated by contract rules, not platform discretion

Character revenue flows into a pool, then is automatically and transparently distributed according to Saga.revenue_config bps settings. The rules live in contracts, so they are auditable and verifiable.

on-chain revenue split · Saga.revenue_config (bps · adjustable)

Participants do not need to understand every chain detail: owning a character automatically makes you part of settlement, and every distribution is visible on-chain.
