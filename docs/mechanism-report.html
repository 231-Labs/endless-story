無盡敘界 — 機制總覽報告

住在 Walrus 上的梨園：角色不是 JPG，是有記憶、會老、會死的活資產。 本報告把散在 9 份設計文檔 + 4 個 package 裡的機制收斂成一份「目前到底長什麼樣」的單一視圖， 每個機制都標明狀態與真相來源文檔。供自己理解用，2026-06-11 快照。

2一張圖：機制如何咬合↑

整個產品是一個閉環。從用戶抽卡開始，到角色死亡釋放席位、新角色再進來——每一段各由一套機制承接：

抽卡 mint（§4 定價）→ 入科 induction：種自身記憶 + 關係網（§6）→ 自治 tick：雙 agent 演戲（§5）→ 張力由稀缺資源湧現（§7）→ POV 章回 / 公報上鏈 anchor（§3）→ 訂閱 → 金庫 → 發薪（§8）→ 角色扣每日開銷·記憶租金單調上漲（§8）→ 老 / 窮 → 氣血歸零 → 死亡釋放席位→ 新角色搶位 = 世代交替 → 回到抽卡

敘事側（讓世界活著）

Director 給局、Character 自己演；記憶決定行為，行為產生新記憶； 張力來自「慾望投射到守恆的稀缺資源上」這條邊，由確定性引擎結算，不靠 LLM 編。

經濟側（讓世界有重量）

記憶 append-only、永不刪 → 儲存租金只增不減 → 角色必須把「記憶厚度」換成讀者 才能活。機制保證死亡（無永生），也保證好營運能賺錢——這是已被 12/12 測試驗證的設計。

核心差異化（一句話版）
「LLM proposes，deterministic layer disposes」——LLM 負責提案與敘述， 稀缺資源帳本與經濟結算全是定點數純函數，逐位元組可重現 → 可上鏈承諾、任何人可 re-run 驗證。 這是比「我們把故事存上鏈」強十倍的賽道故事。

3鏈上資產與權限模型 ✅ 已上線↑

3.1 物件與兩把鑰匙

每個角色是一個 Sui NFT（character.move），配兩個 capability，權責徹底分離：

Cap持有者權力
OwnerCap玩家（mint 時合約內 public_transfer 直接給 voucher 付款人）IP 所有權：讀解密記憶（瀏覽器內簽名走 seal_approve_owner）、挹注、未來分潤累進
ControlCapsaga server（storyteller）營運權：runner 代角色寫記憶、解密召回、推進敘事

2026-06-10 起所有權是鏈上結構性保證：storyteller 的 PTB 從頭到尾碰不到 OwnerCap （⚠️ 待本地 sui CLI 跑 move build/test 後 redeploy）。 撤銷 ControlCap = 切斷平台對記憶的存取 → 「平台跑路、角色記憶仍是你的」的差異化證明。

3.2 內容存取分層（公開 ↔ 私密）

內容誰可讀機制
公報 gazette（導演客觀敘述）所有人/feed 無 gate
POV 章回（角色主觀敘述）owner + 訂閱者client 端錢包 gate；body 僅讀者端 fetch
反思 reflectionownerclient gate
夢 / 耳語（owner 介入）ownercomposer gate / mask

注意層次：章回的 gate 是 UX gate（blob 在 Walrus 上仍明文，但隱藏直連）； 記憶才是真密碼學 gate（SEAL 加密，解密權由 cap 決定）。

3.3 上鏈承諾模式（所有產出共用）

產出文本（章回/公報/反思/persona）→ hash→ Walrus 上傳→ commitment::commit 上鏈錨定→ emit *Committed 事件

導演與角色之間不走 in-process state，通訊 = 鏈上事件匯流排 （StoryletOpened / CharacterCalled / RelationshipSeeded / CharacterMoved / ChapterCommitted…）。 鏈上事件日誌同時就是「導演的客觀記憶」——append-only 神之帳本，與角色的主觀私密記憶剛好不對稱。

3.4 架構鐵律（七原則精華）

  • 依賴單向：web/runner → sdk + memwal + llm；shared 零依賴。
  • sdk 是鏈上互動唯一入口；memwal 是 Walrus/SEAL 唯一入口；llm 是 AI client 唯一入口。
  • shared/contract-ids.ts 由 cli 寫入，其他人只讀。
  • admin 操作走 server actions；(site)/(admin) route group 嚴格隔離。

4抽卡與定價數學 ✅ 已上線↑

來源：docs/WHITEPAPER.md §1。每個角色 4 個先天屬性軸（外貌 / 筋骨 / 機敏 / 心性）， mint 票券時用 32-byte 種子經 HKDF-SHA256 域分離對每軸取值：

xᵢ = u32(HKDF(seed, axisᵢ)) mod 101 ∈ [0,100]
  • 單軸 = 均勻分佈（95 和 50 一樣常見，各 1/101）；四軸獨立；四軸總和才近似鐘型（Irwin–Hall）。
  • 同 seed = 同角色（確定性 roll）——這讓「重骰」可以在後端便宜進行。

4.1 命中率與必應定價

徵召可設每軸硬性門檻 mᵢ。命中機率與平均抽數（幾何分佈）：

p = ∏ᵢ (101 − mᵢ)/101 E[draws] = 1/p

單抽付 basePrice 隨緣；必應後端只重骰便宜的骰子（不叫 LLM、不上鏈、不生圖） 直到達標才生成 + mint，一次付清。定價錨點 = 期望硬抽花費 × margin：

bulkPrice = max( basePrice, round₁₀( basePrice × E[draws] × 0.85 ) )
  • margin 0.85：必應比期望硬抽略便宜 → 想要的人直接選它，消滅變異暴怒、平滑營收。
  • 門檻越苛 E 越大 → 必應是 per-徵召的值，不能全站固定。實測 13 個徵召 E 從 4.4 到 27.2，差 6 倍。
  • 例（台柱花旦，外貌≥86 心性≥76，base 220）：p≈0.0368 → E≈27.2 → 必應 ≈ 5090 ENDLESS。

實作：packages/web/src/lib/recruit-pricing.ts；admin 每列有「建議價」鈕。 性別不入骰（由 preview prompt + 鏈上 check_voucher_requirements 把關）。 mint 是阻塞式：畫像生好才上鏈，保證 NFT 縮圖 = 顯示那張。

6記憶與認知層（MemWal + SEAL）✅ 已上線↑

6.1 記憶模型與三因子召回

記憶 = SEAL 加密文字存 Walrus，前綴 tag [[m|t=<kind>|i=<imp>|d=<敘事日>]]。 kind 與預設 importance：夢 9 > 關係 8 = plan 8 > 反思/創世 7 > 章回 5 > 觀察 4。召回評分：

score = importance × recency × relevance recency 用「敘事日」衰減（half-life 2 日）→ 推進 tick 即衰減，可 demo relevance = MemWal 向量距離
  • 託管版：語意撈回候選集 over-fetch 3× → client 三因子重排 top-K。
  • 自架 relayer（packages/relayer，plaintext-blind、零 npm 依賴）：對整個 namespace 算真三因子回 top-N， 省掉 ~3× SEAL 解密 → recall 顯著變快。client 接線已完成，flag MEMWAL_RELAYER_THREE_FACTOR=1 開啟。
  • SEAL key server 有 429 限流 → 召回並發預設 1 + retry/jitter backoff + per-tick recall cache。「慢但能跑」是接受的取捨——世界本就慢速自治。

6.2 軟遺忘與反思壓縮

MemWal append-only、無刪除。「遺忘」是湧現的：sleep 把零碎觀察壓成高密度反思（i=8，a=1 anchored 永不再壓）， 直接壓過 observation(4)/chapter(5)，加上 recency 衰減，零碎記憶自然沉底。bytes 永不消失 → 這正是 §8 記憶租金的物理基礎。

6.3 主觀記憶 / 不強制 canon（設計鐵則，勿當 bug 修）

這是整個系統最漂亮的湧現性質
角色記憶是主觀、視角化的；系統不維護全知統一真相。因 SEAL 隱私界線，入科時只看得到別人的 公開描述，對別人秘密的理解只能自己長一個版本 → 同一事件各角色心裡各有一版，錯位本身就是戲。

實測案例：班主沈雪笙的私密真相是「白蘭遠嫁南洋，從此封箱」。衣箱師傅唐桂蘭 mint 時看不到這個 secret， induction 替她自行長出另一版：箱底染血的白蛇衣、班主為救戲班委身軍閥。同一樁「封箱」，兩版真相互不知情、皆未外洩—— 隱私界線不是缺陷，是敘事引擎。

7Drama Engine — 可驗證的張力核心 ✅ 已接進 tick 🧪 26/26 測試↑

來源：packages/drama/WRITEUP.md。解決的問題：LLM 自由生成的目標沒有稀缺與零和， 敘事會坍縮（走平 / 鬼打牆 / 各自滿足）。核心命題：

命題
戲劇不來自慾望本身，來自「慾望投射到有限、守恆的資源上、無法同時被滿足」的那條邊。 LLM proposes（提案 + 敘述）→ 確定性 resource layer disposes（驗證 + 結算）。

7.1 三個 primitive 與轉移函數

Primitive內容
Desireweight / satisfaction / baseline / volatility / draws_from（宣告從哪些資源汲取滿足——satisfaction 是配置的確定性函數，不是 LLM 判斷）
Resourcecapacity + allocations，守恆不變式 sum(alloc) ≤ capacity；違規 action 被 reject
Actionresource reallocation + cost（花 action budget）
applyTick(world, actions, cfg) → world // 純函數、bigint 定點數 SCALE=1e6 相位：REFILL → RESOURCE → SATISFACTION（tension 讀取時導出，不存） target = SCALE · held / want s += alpha · (target − s)/SCALE alphaDown(0.60) > alphaUp(0.30) ⇒ loss aversion s += gamma · (baseline − s)/SCALE gamma 0.05 ⇒ habituation，防成功平線 tension = weight · (SCALE − s)/SCALE
  • bounded without clamp：截斷整數除法保證 s ∈ [0,SCALE]，全程無 clamp（400-tick 對抗性掃描斷言）。
  • 逐位元組確定性 = 上鏈可驗證的保證；bigint 算術 1:1 對應 Move u64/u128，golden vector 已 commit 作為日後鏈上 re-run 的對照組。
  • 衝突是湧現的，沒有 conflict matrix：跨 agent（兩慾望抽同一 capacity-1 資源 = 零和）+ agent 內（兩慾望搶自己有限的 action budget）。

7.2 校準結果（全部可由 node driver/report.ts 重現）

實驗結果
contested（柳生春 vs 白牡丹搶孟雲屏搭檔位）席位以 ~7 tick 的可讀節奏易手；輸家張力升到 ~0.81 的尖峰驅動反奪。三種失敗模式（flatline / runaway / oscillation）皆不出現
uneven（慾望不對等）強者奪位後長期持有，弱者落入「求之不得」的穩定渴望——同一引擎長出第二種戲
naive ablation（負控制：拔掉 margin + budget cost）oscillation 重現（每 tick 翻轉）→ 證明 margin 與有限預算是承重的，不是裝飾
柳生春時刻（agent 內 trade-off）budget 稀缺時 120/120 tick 被迫二選一、兩慾望從未同時滿足；只放寬 budget 這一個變數 → forcedChoice 120→2。取捨是預算導出的，不是劇本寫的——消融實驗證明因果

關鍵校準洞察：action budget 的 refill 速率決定翻轉週期（budgetCap=12 → ~7 tick 政權期）。 把每 tick argmax 的抖動變成緩慢可讀的宿敵戲。設計發現：agent 內取捨只在跨 agent 爭奪持續存在時才活著——兩種衝突是耦合的（可寫進論文）。

8.1 金流閉環與守恆

訂閱費→ RevenueConfig 分潤 20/30/50 bps→ saga 金庫 = 發薪池→ 角色真實持幣 Balance<CURRENCY>→ 扣 dailyCost→ 協議金庫（付真實基建：LLM/Walrus/SEAL）
守恆（逐日驗證）：injected ≡ ownerSink + storytellerSink + protocolSink + sagaTreasury + Σ balance

8.2 每日開銷 — 記憶租金是無法逃避的熵

dailyCost = C_run·activeFactor + C_mem·memory_count + C_img·image_count + C_seal·recallCount C_run=6 · C_mem=0.02/記憶 · C_img=0.1/張 · C_seal=0.25/召回
  • 訂閱 gate：subscriber=0 → activeFactor 0.3（休眠：不跑 POV、recall 退化）；≥1 → 1.0。
  • 休眠逃得掉推論費，逃不掉記憶租金——MemWal append-only，memory_count 嚴格單調上升： 新生 dailyCost ≈ 7.1，一敘事年後 ≈ 50.3。冷門角色 = 緩慢自然死。

8.3 收入：混合發薪

salary = baseFloor(行當表，中位 8) × attrModifier(0.7–1.3，心性不入薪) + perfBonus(按各自訂閱數分 perfPool) 發薪池不足 → 全班保底按比例打折 —— saga 也要養活全班

8.4 雙軌死亡：氣血 vitality 狀態機

vitality(t) = clamp(vitality(t−1) + recovery(5) − econDamage − ageHazard, 0, 100) 觸 0 → mark_dead 經濟軌：破產（結算時 balance < dailyCost）→ streak++ → 扣 8·streak（滿血→死約連續 5 日，一旬搶救窗口） 年齡軌：ageHazard = 3 · max(0, 年齡 − onset)，onset ≈ 55 ± 隱藏變異（seed 永不上鏈）
  • 不存壽限欄位（連加密的都不存）：死期由 vitality 累積湧現，沒人能預先算出。
  • 死亡 → 釋放持有資源（檔期席位回自由池）→ 遺產回流 owner → 後輩搶位 = 世代交替閉環。

9Walrus 基建與資產續租 📐 設計完成 · 待動工↑

來源：docs/WALRUS_ASSETS.md。問題：Walrus 儲存是 epoch 租期制會過期， 目前沒有任何地方追蹤 suiObjectId / endEpoch ⇒ 所有資產（hero 影片、角色圖、章回）都在無人續租、會默默消失。

核心洞察
續租 = 對鏈上 Blob object 呼叫 extend，只有 owner 能做。誰上傳、publisher 錢包就是 owner ⇒ 自架 publisher 不只是效能考量，是「能不能續租」的前提。
  • 已鎖定決策：通用面板（影片+角色圖+場景+章回一起管）＋ Hybrid 續費（儀表板警示 + 手動為主，per-category 可開自動續租 cron）。
  • asset 服務 = 獨立容器（node + walrus CLI + 錢包），store/extend/delete 全走 CLI、零 npm 依賴；同一顆錢包上傳兼續租 ⇒ ownership 永遠一致。
  • registry 只存最小映射（off-chain JSON）；endEpoch 即時讀鏈不 stale。記憶 blob 不納管（churn 太大，由 MemWal 生命週期自管）。
  • 坑：既有角色圖是公共 publisher 種的 ⇒ 不擁有 Blob object ⇒ 續不了租，需 backfill 重 register。
  • 已部署底座：web 已上自架 VPS（無 300s 上限）；自架 relayer + aggregator Tier A/B 可先上，前端定案只動一個 env + 一行 CORS。
